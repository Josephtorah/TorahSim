# TRACE RT — running the interpreter one step at a time · 2026-08-01

Written at owner order, capturing the answer to: *"can you run the
interpreter one line at a time and show me what is going on? is that
called a trace route? what do developers do for this?"*

## 1. The words

- **Trace / stepping through** — the right terms: watching a program
  execute one step at a time, seeing state change as it goes.
- **traceroute** — a different tool entirely (network diagnostic: maps
  the path packets take across routers on the internet). Name
  coincidence only.
- **Debugger** — the interactive version of tracing (see §4).

## 2. What developers actually do — three tiers

| tier | tool | what it gives | when used |
|---|---|---|---|
| 1 | **debugger** (Python: `pdb`; IDEs have visual ones) | pause anywhere (a *breakpoint*), step one PYTHON LINE at a time, inspect any variable live | hunting a bug |
| 2 | **trace logging** | the program narrates its own state as it runs; repeatable, shareable, non-interactive | auditing a run — what our machine does |
| 3 | **tests / assertions** | don't watch it run; assert the END states | proving nothing broke — our `--scenarios` flag |

## 3. Our machine's built-in trace (tier 2)

```
python3 run_unit.py <unit_id> --trace
```

Granularity: **one VERSE-STEP at a time** — the natural "line" of this
machine (a Python-line trace exists too; that is tier 1, §4). For every
boot step it prints: the step header, the Hebrew + transliteration +
English, each operator AS IT EXECUTES with the TIR rule it cites, then
the **Δ (delta) line** — all six registers AFTER the step.

Anatomy of one step (gen_01, verse 1:3):

```
STEP_Gn_1_3  Gen.1.3  [DECLARE_LET_RESULT]        <- verse + step label
  he: וַיֹּאמֶר אֱלֹהִים יְהִי אוֹר וַיְהִי־אוֹר
      va-yomer Elohim yehi or va-yehi or | God said: let there be light — and there was light.
   - DECLARE   DECLARE(Elohim, LET(exists(or)))   [TIR-026]   <- operators, in order,
   - TRIPLE    { P: 1:2 state } yehi or { Q: exists(or) }        each citing its rule
   - RESULT    HOLDS(exists(or), t1) — queue popped same verse
  Δ WORLD=['aretz', 'or', 'shamayim'] +presup:4 | SPECS q:0 | TESTS:0 |
    REG writes:0 | LEDGER:[] | FLAGS:4              <- registers AFTER the step
```

**Reading consecutive Δ lines top-to-bottom IS watching the machine
operate**: `or` appears in WORLD the moment RESULT fires (1:3); TESTS
goes 0→1 at the first tov verdict (1:4); LEDGER `[]`→`[1]` at the first
commit (1:5). Register-by-register, the week assembles.

Signature Δ moments across the nine frozen units:

- **gen_06** — SPECS queue holds the council's CMD-US? demand OPEN
  mid-unit; the dominion TRIPLE stands undischarged in the final state.
- **gen_07** — the quietest trace in the corpus: no DECLARE, no TEST,
  no COMMIT ever fires; the LEDGER's Δ never changes — the open
  transaction visible as a column of unchanging `LEDGER:[]`.
- **lev_13** — after the one frame EVENT, every Δ line grows only
  WORLD facts (case + handlers): the law installs; nothing executes.
- **gen_08** — the first trace that ENDS IN DEBT: final Δ shows
  `SPECS q:2` (the permission and the prohibition, both OPEN) and a
  standing penalty handler in WORLD. Every unit before it ended
  settled.

The one-command sweep of every frozen unit:

```
for u in gen_01_creation_boot gen_02_raqia_day gen_03_double_build \
         gen_04_lights_calendar gen_05_swarms_blessing \
         gen_06_land_adam_dominion gen_07_completion_sanctity \
         gen_08_toledot_garden_first_rule lev_13_intake_quarantine; do
  python3 run_unit.py $u --trace
done
```

Traces are DETERMINISTIC: frozen YAML in, same trace out, every time —
they are a rendering of the frozen units, never a source of truth, so
they are regenerated on demand rather than stored (Pre-Code: the YAML
is the artifact; code only interprets).

## 4. The debugger path (tier 1), if ever wanted

```
python3 -m pdb run_unit.py gen_01_creation_boot
```

Then at the `(Pdb)` prompt: `b h_declare` (breakpoint where DECLARE
executes) · `c` (continue to it) · `n` (next line) · `s` (step into) ·
`p m.SPECS` (print the SPECS register live) · `q` (quit). This steps
the PYTHON, one source line at a time — useful for debugging the
interpreter itself, not for reading a derivation.

## 5. Granularity ladder, summarized

| level | steps by | tool |
|---|---|---|
| verse | boot step + Δ registers | `--trace` (built-in) |
| operator | each DECLARE/EVENT/… line | visible inside each step's trace block |
| Python line | interpreter source | `pdb` |
| end-state only | scenario assertions | `--scenarios` |

*Experimental model — not binding religious law.*
